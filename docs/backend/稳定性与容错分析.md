## 一、文档背景与目标

### 1.1 背景

### 1.2 目标

* **出问题时系统能自愈/可降级/可定位**
* 明确各类失败场景的应对策略
* 确保多实例部署下的数据一致性
* 提供可追溯的容错改进路线图

## 三、重试 / 超时 / 熔断机制

### 3.1 重试机制

#### 现状
- ❌ **全局缺失**：无自动重试逻辑
- ⚠️ **手动补偿**：`GuestCleanupService` 中对单个用户删除失败会继续处理下一个，但不会重试失败的用户

**改进建议**:
```typescript
// 建议：通用重试装饰器
function Retry(maxAttempts: number, delay: number) {
  return (target: any, propertyKey: string, descriptor: PropertyDescriptor) => {
    const originalMethod = descriptor.value;
    
    descriptor.value = async function (...args: any[]) {
      let lastError;
      for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
          return await originalMethod.apply(this, args);
        } catch (error) {
          lastError = error;
          if (attempt < maxAttempts) {
            await new Promise(resolve => setTimeout(resolve, delay * attempt));
          }
        }
      }
      throw lastError;
    };
  };
}

// 使用示例
@Retry(3, 1000)
async deleteAccount(userId: string) {
  // ... 删除逻辑
}
```

### 3.3 熔断机制

#### 现状
- ❌ **全局缺失**：无熔断器实现
- ⚠️ **部分降级**：`StorageService` 删除文件失败不抛异常（被动"熔断"）

**改进建议**:
```typescript
// 建议：实现简单熔断器
class CircuitBreaker {
  private failureCount = 0;
  private state: 'CLOSED' | 'OPEN' | 'HALF_OPEN' = 'CLOSED';
  
  async call<T>(fn: () => Promise<T>, threshold = 5): Promise<T> {
    if (this.state === 'OPEN') {
      throw new Error('Circuit breaker is OPEN');
    }
    
    try {
      const result = await fn();
      this.reset();
      return result;
    } catch (error) {
      this.failureCount++;
      if (this.failureCount >= threshold) {
        this.state = 'OPEN';
        setTimeout(() => this.state = 'HALF_OPEN', 60000); // 1分钟后半开
      }
      throw error;
    }
  }
  
  private reset() {
    this.failureCount = 0;
    this.state = 'CLOSED';
  }
}
```

### 4.1 文件删除与 DB 事务分离

#### 现状

```typescript
      await this.storageService.deleteFile(file);
    } catch (error) {
      // 记录到失败队列，定时重试
      await this.orphanedFilesQueue.add({ file, userId: user.id });
    }
  }
}
```

## 五、任务调度与幂等

### 5.1 GuestCleanup 任务分析

#### 幂等性设计

**实现** ([guest-cleanup.service.ts](file:///Users/zhengjiyuan/Desktop/iPet/iPet-BackEnd/src-backend/guest/guest-cleanup.service.ts)):
```typescript
private async runOnce() {
  if (this.running) {
    return; // ✅ 单实例幂等
  }
  this.running = true;

  try {
    const cutoff = new Date(Date.now() - this.retentionMs);
    const expiredGuests = await this.prisma.user.findMany({
      where: {
        isGuest: true,
        lastActiveAt: { lt: cutoff }, // ✅ 基于时间窗口，天然幂等
      },
    });

    for (const guest of expiredGuests) {
      try {
        await this.usersService.deleteAccount(guest.id);
      } catch (error) {
        this.logger.error(`Failed to delete guest user ${guest.id}`, error);
        // ⚠️ 失败后不重试，下次调度会再次尝试
      }
    }
  } finally {
    this.running = false;
  }
}
```

**幂等性保证**:
- ✅ **查询幂等**：基于 `lastActiveAt` 时间戳，重复执行不会重复删除
- ✅ **删除幂等**：用户已删除再次删除会抛异常（被捕获记录日志）
- ⚠️ **部分失败**：某个用户删除失败不影响其他用户，但该用户需等下次调度

### 5.2 多实例并发处理

#### 问题场景

**场景 1: 两个实例同时执行 GuestCleanup**
- 实例 A 和 B 同时发现 100 个过期游客
- 都尝试删除这 100 个用户
- 可能导致：
  - 重复日志
  - 数据库连接压力加倍
  - 文件删除重复尝试

**场景 2: 用户删除中途另一实例更新该用户**
- 实例 A 开始删除用户 X（已删文件，准备删 DB）
- 实例 B 游客登录刷新 `lastActiveAt`
- 实例 A 继续删除 → 用户 X 被错误删除

#### 改进建议

```typescript
// 方案 1: 分布式锁（Redis）
import { InjectRedis } from '@nestjs/redis';
import { Redis } from 'ioredis';

export class GuestCleanupService {
  constructor(
    @InjectRedis() private readonly redis: Redis,
    private readonly prisma: PrismaService,
    private readonly usersService: UsersService,
  ) {}

  private async runOnce() {
    const lock = await this.redis.set(
      'lock:guest-cleanup',
      'locked',
      'EX', 300, // 5分钟过期
      'NX'       // 仅在不存在时设置
    );

    if (!lock) {
      this.logger.debug('Another instance is running cleanup');
      return;
    }

    try {
      // ... 清理逻辑
    } finally {
      await this.redis.del('lock:guest-cleanup');
    }
  }
}
```

```typescript
async runOnce() {
  const startTime = Date.now();
  const metrics = {
    foundCount: 0,
    successCount: 0,
    failureCount: 0,
    duration: 0,
  };

  try {
    const expiredGuests = await this.prisma.user.findMany(/* ... */);
    metrics.foundCount = expiredGuests.length;

    for (const guest of expiredGuests) {
      try {
        await this.usersService.deleteAccount(guest.id);
        metrics.successCount++;
      } catch (error) {
        metrics.failureCount++;
        this.logger.error(`Failed to delete guest ${guest.id}`, error);
      }
    }
  } finally {
    metrics.duration = Date.now() - startTime;
    this.logger.log({ event: 'guest_cleanup_completed', ...metrics });
  }
}
```

## 八、总结与行动计划

### 8.1 核心发现

1. **幂等性设计优秀** → `GuestCleanupService` 通过 `running` 标志和时间窗口查询实现单实例幂等
2. **事务边界清晰** → 数据库操作使用事务，文件操作分离
3. **容错基础薄弱** → 缺少重试、超时、熔断等通用机制
4. **多实例风险** → 限流、任务调度、数据更新存在并发问题
